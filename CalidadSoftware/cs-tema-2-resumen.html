2.0 El proceso de revisión

Objetivo y vocabulario de los apuntes

Las revisiones son filtros tempranos: descubren problemas antes de que lleguen al usuario. Pocas revisiones dejan pasar errores; demasiadas frenan el flujo. Se revisan código, diseño, requisitos, pruebas, documentación y configuración.

Según la terminología de este tema, error es un problema identificado durante el desarrollo antes de la entrega; defecto es el detectado tras la entrega o el que se propaga de una actividad estructural a otra. El resultado de la revisión es una lista de hallazgos y el estado del producto.

Fagan (1976): seis fases, hoy aplicadas al PR

  1. Planificación: alcance, objetivo, riesgos, reglas de negocio, revisores y pruebas; señalar intervención de IA y zonas críticas.
  2. Preparación: autor aporta PR pequeño, intención, ticket, pruebas y evidencias; revisor entiende requisitos y contexto antes de juzgar líneas.
  3. Revisión o examen: autoevaluación, pares, análisis estático, tests, SCA e IA; las decisiones de alto impacto requieren criterio humano.
  4. Registro y clasificación: comentarios trazables: bloqueante, importante, menor, pregunta, sugerencia o fuera de alcance.
  5. Corrección y seguimiento: nuevos commits, reejecución de comprobaciones y nueva revisión cuando proceda; comprobar también regresiones.
  6. Cierre: puede extenderse al despliegue, logs, métricas, incidencias y mejora de checklists.

Cinco niveles de planificación en cascada

Producto (necesidad de negocio, creación del ticket) → ticket (criterios, alcance y riesgo en refinamiento) → técnica (implementación y arquitectura) → PR (historia clara al pasar a Ready for Review) → revisión (asignación de expertos/Code Owners).

Un atasco en revisión puede venir de criterios de aceptación ausentes o de asignar tarde al experto. Diagnosticar el nivel que falló es más útil que pedir aprobaciones más rápidas.

2.1 Métricas y flujo de valor

Se mide el sistema de trabajo del equipo, no el rendimiento individual. Value Stream es el recorrido de la necesidad hasta el valor en producción.

MétricaInicio y fin en estos apuntesDiagnóstico

Cycle TimePrimer commit → merge y despliegueEficiencia del desarrollo.

Tasa de rechazo de PRsPRs con cambios significativos solicitados / PRs revisados × 100Retrabajo en revisión.

El PDF agrupa «Change Failure Rate / Tasa de Rechazo». Conviene distinguir ambos eventos y denominadores: devolver un PR y fallar en producción no son lo mismo. Los límites temporales anteriores son los usados en la asignatura.

Ley de Little

L = λ · W: trabajo medio en el sistema = tasa media de llegada × tiempo medio de permanencia, en un sistema estable y con unidades compatibles. WIP es el trabajo abierto sin terminar. A tasa constante, menos WIP implica menor tiempo medio.

Ejemplo: 6 PRs en el sistema y 2 PRs/día → W = 3 días. Lead Time 14 días, Cycle Time 3 días e Idle Time 48 h → dos tercios del ciclo (≈67 %) esperando; el cuello de botella está en revisar.

Prácticas y trampas

  • Micro-PRs: recomendación de los apuntes de 200–400 líneas modificadas, excluyendo generadas/configuración; dividir cambios grandes con PRs apilados.
  • Límite WIP: si se satura revisión, terminar/revisar antes de iniciar más trabajo.
  • Goodhart: convertir una métrica en objetivo puede provocar rubber-stamping (aprobar sin leer). Contrastar velocidad con rechazo, incidentes y tamaño del PR.
  • DORA: relaciona flujo con frecuencia de despliegue, Lead Time para cambios, Change Failure Rate y recuperación (MTTR). No confundir Lead Time para cambios con el recorrido completo de una petición.
  • Empezar con pocas métricas entendidas; evitar dashboards que no llevan a decisiones.

2.2 Pull Requests y comunicación

GitHub Flow

Rama desde main → commits → PR → discusión/revisión → merge aprobado → despliegue. Ramas efímeras: corta vida, idealmente menos de 2–3 días según los apuntes.

Un PR transmite contexto: qué cambia, por qué (ticket), cómo probarlo y evidencia visual cuando aplique. Un PR huérfano obliga a adivinar. Empatía cognitiva = anticipar las dudas del revisor y razonar las sugerencias sin atacar al autor. Cada aclaración entre zonas horarias puede costar hasta una jornada.

Conventional Commits

tipo(ámbito opcional): descripción, con cuerpo y pie opcionales. fix: → PATCH; feat: → MINOR; ! o pie BREAKING CHANGE: → MAJOR. Ejemplo: feat(parser): add arrays. Permite automatizar versiones y CHANGELOG.

Otros tipos: build (compilación/dependencias), ci, docs, style (sin cambio semántico), refactor (sin nueva función ni corrección), perf, test y chore. El PDF asocia perf a PATCH; los efectos adicionales dependen de la política de publicación configurada.

Conventional Comments

label (decorations): asunto, más explicación si hace falta. issue: problema; suggestion: mejora; nitpick/nit/quibble: detalle trivial; question: aclaración; chore: tarea de proceso; todo: pequeño cambio necesario; praise/kudos: elogio; thought: idea futura; note: observación; typo: errata; polish: pulido.

(blocking) impide merge; (non-blocking) no lo impide; (if-minor) resolver solo si es trivial. La decoración aclara la obligación concreta. Ejemplo: issue (blocking): falta validar el límite de edad.

Coordinación

  • Draft PR / RFC: abrir pronto para validar arquitectura antes de invertir en detalles; evita la falacia del coste hundido.
  • CODEOWNERS: mapea rutas a equipos. Para exigir aprobación se combina con reglas de protección de rama.
  • Bus Factor: cuántas pérdidas de personas comprometen el proyecto; 1 indica conocimiento concentrado. Revisiones cruzadas y rotación reducen silos.
  • Bikeshedding: debatir estilo trivial mientras se ignoran riesgos; automatizar formato con linters.
  • Evitar review dumps y ghosting. Primera respuesta en un día laborable; sesiones de hasta 60 min. En módulos críticos, dos aprobaciones, una del propietario; tras dos rondas sin acuerdo, conversación breve.

2.3 IA y validación de alucinaciones

Un LLM genera secuencias probables; plausibilidad, legibilidad y explicación convincente no demuestran corrección. Zero-Trust exige verificación independiente. Automation Bias es confiar por venir de una máquina; Halo Effect es atribuir corrección a una explicación brillante.

Cinco focos de auditoría

  1. APIs inventadas: verificar firma y existencia del método en la documentación de la versión instalada.
  2. Happy path: buscar fallos de red, timeout, reintentos y circuit breaker cuando correspondan; contemplar vacíos, límites y errores.
  3. Seguridad: revisar autenticación, tokens y contraseñas; detectar propuestas obsoletas o criptografía casera.
  4. Semántica de negocio: un endpoint puede compilar y omitir la edad mínima o una restricción financiera.
  5. Tests tautológicos: código y test pueden compartir el mismo supuesto incorrecto. Diseñar casos desde requisitos, con revisión humana independiente.

Pruebas de mutación

Introducen fallos deliberados (cambiar operadores o condiciones). Un mutante muere si los tests detectan el cambio; sobrevive si pasan pese a él. Mutation Score = mutantes detectados / mutantes evaluados × 100 (interpretar el denominador conforme a la herramienta). No equivale a cobertura de líneas.

IA como primer filtro: resumir cambios y señalar patrones. La decisión final requiere criterio humano; no conceder auto-merge irrestricto al agente. Reservar la atención humana a negocio, seguridad, arquitectura y comportamiento bajo fallos.

2.4 SAST, SCA y cadena de suministro

ConceptoQué aporta
SASTAnaliza código propio sin ejecutarlo: inyección, XSS, secretos. Motores semánticos usan AST y análisis de flujo.
SCAExamina componentes de terceros, directos y transitivos, y contrasta versiones con vulnerabilidades conocidas.
SBOMInventario de componentes y versiones del producto; puede firmarse y vincularse al artefacto.
SLSAMarco para reforzar y verificar procedencia e integridad del proceso de construcción.
VEXDeclara el estado de explotabilidad de una vulnerabilidad en el producto, con justificación auditable.

Análisis de flujo y dependencias

Taint Analysis: seguir datos desde una Source no confiable hasta un Sink sensible y comprobar las defensas. SQL injection manipula consultas; XSS ejecuta scripts en páginas de otras víctimas. Las consultas parametrizadas separan instrucciones y datos; evitar filtros caseros. Un ORM no protege si se concatenan entradas en SQL crudo.

Una dependencia directa se instala expresamente; una transitiva llega por otra. El SCA debe recorrer el grafo completo. CVE identifica públicamente una vulnerabilidad conocida; un escaneo limpio no demuestra ausencia de fallos desconocidos.

Integridad y remediación

El caso SolarWinds ilustra que también puede atacarse el build. Inventario, hashes, firmas y evidencias de procedencia se complementan: un SBOM por sí solo no prueba que el proceso de construcción sea seguro.

Keyless Signing: identidad del pipeline mediante OIDC, credenciales/certificado efímeros y firma con Sigstore/Cosign; Rekor registra evidencias. Evita gestionar una clave de firma permanente. VEX documenta por qué una ruta vulnerable no es explotable en el contexto analizado; no equivale a ignorar una alerta.

Herramientas citadas

  • Semgrep / CodeQL: análisis estático; CodeQL permite consultar una representación del código.
  • Trivy / OWASP Dependency-Check: escaneo de vulnerabilidades/componentes.
  • Syft: genera SBOM (SPDX/CycloneDX); Grype: busca vulnerabilidades.
  • Dependency-Track: centraliza SBOMs y permite localizar productos afectados por nuevos CVEs.
  • Dependabot / Renovate: proponen actualizaciones mediante PRs; comprobar compatibilidad y tests.
  • SonarQube: señales de calidad, seguridad y métricas estructurales.
Shift-Left: análisis en IDE/pre-commit y después en CI. Configurar gates según riesgo; automatizar lo mecánico y revisar las excepciones con evidencia.

2.5 Revisión estructural y métricas

Funcional: ¿cumple el ticket? Evidencia: tests, demo, aceptación. Estructural: ¿será fácil cambiar, probar y extender? Evidencia: dependencias, cohesión, métricas y smells. Un sistema puede funcionar y acumular deuda técnica.

Dónde y cómo mirar

Hotspot = complejidad + cambios frecuentes (churn). Priorizar archivos altos en ambas dimensiones. Lehman: la complejidad crece si no se reduce activamente. Conway: el software tiende a reflejar la comunicación de la organización.

  1. Macro: capas, dependencias, ciclos, arquitectura y ADRs.
  2. Meso: clases, responsabilidades, puntos de variación y abstracciones.
  3. Micro: funciones, nombres, parámetros, errores y efectos secundarios.

Primero CI y Quality Gate, después criterio humano. Un comentario útil contiene síntoma → principio → refactorización propuesta. Bloquear violaciones de capas, ciclos o nueva lógica de negocio duplicada; registrar deuda previa fuera de alcance sin desviar el PR.

Son señales, no órdenes automáticas de refactorizar. Comparar con la rama base (Clean as You Code) y combinar métricas: un parser complejo no se juzga igual que un servicio complejo que cambia cada semana.

Acoplamiento e inestabilidad

Ca: módulos que dependen de este (aferente). Ce: módulos de los que depende (eferente). I = Ce / (Ca + Ce): 0 estable, 1 inestable; si ambos son cero, la fórmula no está definida. A es la proporción de abstracciones. D = |A + I − 1|, distancia a la secuencia principal.

Ejemplo: Ca=6, Ce=2 → I=0,25; A=0,75 → D=0. Zona de dolor: A e I bajos, módulo concreto del que todos dependen. Zona de inutilidad: A e I altos, exceso de abstracción sin consumidores. D es una señal de equilibrio, no una garantía global de calidad.

2.5 Código limpio, smells y SOLID

Reglas para leer y cambiar con seguridad

Nombres de negocio; funciones pequeñas con un nivel de abstracción; pocos argumentos; evitar flags booleanos; cláusulas de guarda; constantes con significado; efectos explícitos y errores manejados o propagados. CQS separa consultas y comandos. Demeter evita cadenas de navegación. DRY centraliza reglas de negocio; KISS/YAGNI evita abstracciones sin necesidad; Boy Scout mejora local sin ampliar el alcance.

Code smells: síntomas, no prueba automática de bug

FamiliaEjemplos y respuesta
BloatersLong Method → Extract Method; God Class → Extract Class; Long Parameter List → Parameter Object; Primitive Obsession / Data Clumps → Value Object.
OO AbusersSwitches repetidos → polimorfismo; Refused Bequest → composición; Temporary Field → extraer concepto; interfaces alternativas → unificar/adaptar.
Change PreventersDivergent Change: una clase cambia por muchos motivos → separar. Shotgun Surgery: un cambio toca muchas clases → reunir responsabilidad. Jerarquías paralelas → revisar dependencias.
DispensablesDuplicated Code → extraer regla; Dead Code → eliminar; Speculative Generality → quitar abstracción; Lazy Class → Inline Class; Data Class → acercar comportamiento a datos.
CouplersFeature Envy → Move Method; Inappropriate Intimacy → encapsular; Message Chains → Hide Delegate; Middle Man innecesario → eliminar intermediario.

SOLID

  • SRP: una razón para cambiar/un actor. Mezclar impuestos, SQL y email en InvoiceService sugiere separar responsabilidades. Cohesión alta y acoplamiento bajo.
  • OCP: abierto a extensión y cerrado a modificación. Switches sobre tipos repetidos sugieren Strategy, State o Factory. Regla de tres: refactorizar al tercer caso o cuando se repite el switch en otro sitio; no abstraer todo anticipadamente.
  • LSP: el subtipo sustituye al padre respetando el contrato; no refuerza precondiciones ni debilita postcondiciones. Métodos vacíos/NotImplemented y tests de contrato fallidos son señales.
  • ISP: ningún cliente depende de métodos que no usa; preferir interfaces pequeñas. Las interfaces gordas empujan a violar LSP.
  • DIP: dominio e infraestructura dependen de abstracciones orientadas al dominio. SQL/HTTP concretos dentro del negocio dificultan tests aislados. Adapter y Repository pueden aislar esas fronteras.
DIP ≠ inyección de dependencias ≠ contenedor IoC. Son principio de diseño, técnica para recibir dependencias y herramienta que automatiza su construcción, respectivamente.

Los patrones resuelven problemas concretos: Builder/Factory para construcción, Strategy para comportamiento variable, Adapter/Repository para fronteras, Template Method para esqueletos comunes. Aplicarlos solo cuando aclaren una necesidad real.
